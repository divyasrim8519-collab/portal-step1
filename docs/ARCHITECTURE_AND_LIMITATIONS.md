# Architecture, Design Choices and Limitations

## Architecture

```
Browser (React client components, polling every 3s)
        |  HTTPS, httpOnly session cookie
        v
Next.js on Vercel
  middleware.js        -> redirects, security headers, cross-origin write check
  app/api/**/route.js  -> authenticate -> authorise (role + membership) -> validate (Zod) -> Prisma
  lib/dto.js           -> whitelist mappers for participant responses
  lib/moderation*.js   -> rule engine (pure core + DB wrapper)
        |
        v
Neon PostgreSQL (users, sessions, projects, memberships, conversations,
                 messages, rules, flags, notifications, audit events)
```

## Request flow for a message

1. `POST /api/projects/:id/messages` authenticates the session, then loads the caller's **ACTIVE** membership for that project (404 otherwise).
2. Input is validated (1-2000 characters, safe `clientMessageId`). Sender, membership and status are never accepted from the client.
3. If the `(sender, clientMessageId)` pair already exists, the original message is returned. This makes retries safe.
4. In **one transaction**: the message is checked against enabled rules; it is stored as `DELIVERED` or `HELD`; one flag per matched rule is stored; an alert is created for each active admin.
5. The recipient's `GET` query selects only `DELIVERED` messages plus the requester's own, so held messages cannot reach them.
6. An admin decision runs in one transaction using a conditional update on `PENDING` flags. A repeat or simultaneous decision changes nothing, so a message is never delivered twice. The decision, the sender notification and the audit event commit together.

## Design choices

- **404 instead of 403** for anything the caller should not know exists.
- **Server-side everything.** The UI only reflects what the API allows.
- **Aliases per membership**, generated by the server ("Client A", "Project Specialist B"), unique within a project and independent across projects.
- **Polling instead of WebSockets** because serverless functions cannot hold connections. The messages endpoint returns the latest 200 visible messages so status changes (held to delivered) propagate without extra logic.
- **Pure moderation core** (`lib/moderation-core.mjs`) with no database dependency, so rules are unit tested (`npm test`).
- **Contact sharing cannot be loosened.** Those rules always hold and cannot be disabled; other categories are configurable.
- **Only held messages can be rejected.** A delivered message cannot be taken back from the recipient.
- **Senders are notified only about held messages**, so they do not learn about silent flagging of delivered messages.

## Moderation rules

| Category | Default action | Examples caught |
|---|---|---|
| Contact sharing | Hold (fixed) | phone numbers, emails (including "name at gmail dot com"), @handles and social platform names, URLs |
| Off-platform | Hold (configurable) | WhatsApp, "pay me directly", "outside the platform" |
| Commercial | Allow and flag (configurable) | price, quote, discount, invoice, advance, payment, amounts with $ or ₹ |
| Abuse | Hold (configurable) | insults and threats |

Text is checked in its original form and in a normalised form (obfuscated "at"/"dot", spelled-out digits, separators between digits removed).

## Verified false positives (harmless text that is flagged)

These were run against the seeded rules:

- "The release is on 2026-10-04 14:18 sharp" is **held** as a phone number.
- "Order #1234567890 is ready" is **held** as a phone number.
- "We need a stupid-simple onboarding flow" is **held** as abuse.
- "Our linkedin banner needs a new size" is **held** as a social handle.
- "Please quote the hours for the bug fix" is **flagged** as commercial.

Admins handle these with **Dismiss (false positive)**, which delivers the message.

## Verified missed detections (contact attempts that pass)

- "send me a mail to john at gmail" (no domain ending)
- "pay me on paypal later"
- Digits written as emoji (9️⃣8️⃣7️⃣...)
- Letters spaced apart ("w h a t s a p p me", "tele gram")

Adding patterns reduces but never eliminates this. Determined users can always find phrasing that passes.

## Known limitations

- Pseudonymity is not anonymity. Message content, writing style, timing and shared knowledge can identify a person. Administrators can see everything.
- Not end-to-end encrypted. Messages are stored readable in the database (TLS in transit).
- Polling gives up to a 3-second delay; no typing indicators or presence (deliberately, since online status is hidden).
- Login rate limiting and the rule cache are in-memory per serverless instance.
- Regex rules are English-centric and have the false positives and misses listed above.
- Text only: no attachments or calls.
- One active client and one active employee per project (as designed for this assignment).
- Free-tier cold starts (Neon, Vercel) can slow the first request.
- Automated tests cover the rule engine; API behaviour is covered by `scripts/acceptance.mjs`, which needs a running deployment. There are no browser UI tests.

## Third-party services

Vercel (hosting), Neon (PostgreSQL). npm libraries: Next.js, React, Prisma, Zod, bcryptjs, Tailwind CSS. **No external AI or moderation service is used.**
